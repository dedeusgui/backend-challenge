# Decisions

> **Appendix.** Read after [ARCHITECTURE.md](ARCHITECTURE.en.md). Each row is a decision with its reason, trade-off and
> evidence. The main decisions are gathered in ARCHITECTURE's table at its start.

Every technical decision of this project, with the reason, the trade-off, the evidence and the
status. Decisions with their own record are in [`docs/adr`](docs/adr). The rules of the business
are in [`ARCHITECTURE.md`](ARCHITECTURE.en.md) section 13.

Status values:

- **Accepted**: decided, implemented, and tested.
- **Open**: implemented, but the owner of the specification must confirm it. Each open item is
  listed again in [`docs/INVARIANT_REVIEW.md`](docs/INVARIANT_REVIEW.en.md), section 2.
- **Superseded**: replaced by a later decision, which is named.

## D. Reference rules (business interpretations, IDs R-01 to R-13)

Financial decisions D1–D4 map to rules R-01, R-04/R-05, R-03 and R-06, respectively, and were confirmed on 2026-11-01. These are implemented technical decisions; R-01 and R-06 include interpretations beyond the brief's literal wording. The known limitation is that an unreferenced WIN cannot prove uniqueness per BET. Only Jungle Gaming can clarify whether it intended a different reading of the brief; this is not pending internal approval. See section 13 of `ARCHITECTURE.en.md` and `docs/INVARIANT_REVIEW.en.md`.

| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- | ----------------------------- |
| R-01 | A WIN and a LOSS **may name** the BET they settle. The spec makes the reference optional, and only REFUND and ROLLBACK require one (6.3, 7).                                                                       | Without a reference, a result cannot be checked against a REFUND or a second result, and an unreferenced WIN does not demonstrate settlement uniqueness per BET. | Optional reference per specification; confirmed in the final-delivery instruction dated 2026-11-01. ## E. Concurrency and locking

| ID   | Decision                                                                                                                                                         | Why                                                                                              | Trade-off                                                                                 | Evidence                                                               | Status   |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- | -------- |
| E-01 | The unit of concurrency is the `walletId`. Operations on different wallets never wait for each other.                                                            | The challenge's section 8.                                                                       | A hot wallet serialises its operations.                                                   | `hot-wallet.test.ts`, `distinct wallets` tests                         | Accepted |
| E-02 | Every financial path takes a **pessimistic row lock** on the wallet (`FOR UPDATE`) before it checks the idempotency key or changes anything. See ADR 0001.       | A lock is simpler to reason about than retries, and the lock is the first thing every path does. | Requests on the same wallet queue behind each other.                                      | `findForUpdate`; the lock mutant (M1) is caught by the zero-retry test | Accepted |
| E-03 | The version guard in `save` stays as a second line of defence, with at most 3 attempts on `ConcurrencyConflictError`. Exhaustion is `503` with `retry-after: 1`. | A lock bug must not become a lost update.                                                        | Retries add latency when they happen. With the lock, they never happen (measured).        | `MAX_CONCURRENCY_ATTEMPTS`, `save`, the zero-retry assertion           | Accepted |
| E-04 | Reconciliation takes a **shared** lock (`FOR SHARE`) on the wallet, so a debit waits while it reads the balance and the ledger.                                  | Without it a debit between the two reads is reported as a divergence that does not exist.        | A debit of that wallet waits for one reconciliation.                                      | `findForShare`, `reconciliation-consistency.test.ts`, commit `4d6dc01` | Accepted |
| E-05 | Read paths take no lock. Only reconciliation takes a shared lock.                                                                                                | Reads must never queue behind a financial write.                                                 | A read may see a state that is one commit old.                                            | `WalletQueries`, `WagerQueries`                                        | Accepted |
| E-06 | The outbox claim uses `FOR UPDATE SKIP LOCKED`.                                                                                                                  | Two publishers should not wait for each other.                                                   | Removing it changes nothing a test can see (mutant M3). The lease predicate keeps safety. | `mikro-orm-outbox.store.ts`; M3 recorded in `TEST_STRATEGY.md`         | Accepted |
| E-07 | Lock waits are **not measured**. `concurrency_conflicts_total` counts lost races only.                                                                           | Measuring the wait needs instrumentation that was not added.                                     | A slow lock is invisible in the metrics.                                                  | `process-wager-transaction.use-case.ts`                                | Open     |
| E-08 | A stored transaction is answered before the wallet lock is taken. The fast path is one lookup before the lock, and it is not benchmarked in this review.         | A replay does not queue behind a financial write, and the lock is taken only for a new identity. | None measured.                                                                            | `a replay is answered without waiting for the wallet lock`             | Accepted |

## How the core decisions work in the code

The short versions. Each file has the full version.

**Pessimistic lock on the wallet.** The first query of every financial path locks the wallet row.
Nothing else runs before it, so the replay check and the balance check see the state the lock holds.

```ts
// src/modules/wallet/infrastructure/mikro-orm-wallet.repository.ts
const record = await this.em.findOne(
  WalletRecord,
  { id: walletId },
  { lockMode: LockMode.PESSIMISTIC_WRITE, refresh: true },
);
```

**Version guard on save.** The update names the version it read. If another transaction changed
the row in between, nothing matches, and the caller retries.

```ts
const updated = await this.em.nativeUpdate(
  WalletRecord,
  { id: wallet.id, version: expectedVersion },
  { balance: wallet.balance.toString(), version: wallet.version, updatedAt: wallet.updatedAt },
);
if (updated !== 1) throw new ConcurrencyConflictError(/* ... */);
```

**Idempotency.** The key is a unique row in the database, under the provider. The replay path
returns the stored result, so a repeat never reaches the balance.

```sql
CONSTRAINT wager_idempotency_key UNIQUE (provider_id, idempotency_key)
```

**One result per BET, and one reversal per reference.** The settlement function checks the rule,
and a partial unique index enforces it, so a second writer cannot break it.

```ts
// src/modules/wagering/application/transaction-settlement.ts
if ((await repositories.wagers.processedOutcomesOf(reference.id)).reversed) {
  return this.reject(repositories, transaction, wallet, 'REFERENCE_ALREADY_REVERSED', options);
}
```

**Outbox claim with a lease.** A publisher claims rows it can lock, and the lease token says who
owns each row. The completion writes only if the token still matches.

```sql
UPDATE outbox_messages SET lease_token = ?, lease_expires_at = ?
 WHERE id IN (SELECT id FROM outbox_messages
               WHERE published_at IS NULL AND next_attempt_at <= ?
                 AND (lease_expires_at IS NULL OR lease_expires_at < ?)
               ORDER BY next_attempt_at LIMIT ?
               FOR UPDATE SKIP LOCKED)
RETURNING ...
```

**Acknowledge after commit.** The consumer deletes the queue message only after the transaction
has returned. A crash in between leaves the message in flight, and the redelivery is safe because
of the inbox row.

```ts
// src/modules/messaging/application/inbound/wager-command-consumer.ts
if (disposition === 'APPLIED') {
  await faults.beforeAcknowledge(message); // test seam, a no-op in production
  await queue.acknowledge(message.receiptHandle);
}
```

**Held reference with bounded backoff.** The delay doubles from 1 s and is capped at 5 min. After
six misses the transaction is rejected, and the rejection is announced.

```ts
export function referenceRetryDelayMs(missesSoFar: number): number {
  return Math.min(BASE_DELAY_MS * 2 ** missesSoFar, MAX_DELAY_MS);
}
```

**Reconciliation takes a shared lock.** The read of the balance and the read of the ledger
happen under the same shared lock, so a debit waits between them.

```ts
const wallet = await repositories.wallets.findForShare(walletId); // FOR SHARE
const summary = await repositories.ledger.summarize(walletId, wallet.currency);
```

**API keys.** A key is 256 random bits. Only its SHA-256 hash is stored, and a request is
authenticated by hashing its key and looking the hash up.

```ts
export function hashApiKey(key: string): string {
  return createHash('sha256').update(key).digest('hex');
}
```

**Provider scope.** The controller checks the provider of the request before the use case runs.

```ts
export function requireProviderScope(principal: Principal, providerId: string): void {
  if (!canOperateFor(principal, providerId)) {
    throw new ForbiddenException('This API key may not act for this provider');
  }
}
```

## P. Decisions of the finalization review

Each decision names its evidence. The commit that made it is in the git log. Decisions that rest on a
measurement state the host, and every figure comes from `docs/LOAD_TEST_RESULTS.md` or from a test.

- **P-01 The replay contract is kept.** A replay returns one stored snapshot per transaction: the status and
  the balance it had when it reached its current state. A held operation answers 202 with the balance it was
  held with, and after resolution it answers its outcome with the balance then. The specification's "original
  result" is read this way, because a pending operation has no result yet. ARCHITECTURE section 6 has the table
  question by question, with the test that proves each answer. No second state machine or snapshot table was
  added. Cost if wrong: a provider that expects 202 forever after resolution must read the status instead.
- **P-02 The two-decimal money rule is verified, not changed.** `b5ba60d` already refuses `25` and `25.1` on
  every path, and the matrix row MNY-01 is backed by suites that pass at HEAD. Cost if wrong: none found.
- **P-03 One parser for the business fields of HTTP and of the queue** (`d437452`). A queue command with a
  walletId that is not a UUID is dead-lettered at once, as HTTP refuses it. Before, it reached PostgreSQL, was
  classified as transient, and was retried ten times. A control character in the Idempotency-Key is refused on
  both paths. Cost if wrong: a queue producer that sent non-UUID walletIds would now see them dead-lettered. The
  specification's examples are UUIDs.
- **P-04 The dead-letter copy has a content-derived deduplication id** (`ebc9589`). A crash between the
  dead-letter send and the acknowledgement leaves one copy, not two, while the broker's five-minute window lasts.
  After the window a redelivery adds another copy, so nothing is lost. Cost if wrong: a copy consumed and deleted
  inside the window is not re-created by the same content. Its content is the same message, so nothing is lost.
- **P-05 A duplicate that waits for the wallet lock records no second inbox row** (`a10fd11`). It was rolling back
  and counting a lost race that was not one. The lost-race counter now means what its name says. The duplicate
  check under the lock runs only on that path, so a new command pays nothing for it.
- **P-06 The outbox sends claimed batches in requests of ten, and it claims in due order** (`89b7bc1`).
  Measured with paired runs on two CPUs: the agreed rate rose from 100 req/s to 150 and 200, and the CPU that
  LocalStack used per request fell by about three quarters. The ordering defect it fixed was real: `UPDATE ...
RETURNING` does not keep the subquery's order. Events of one wallet that share a timestamp have no defined
  order, and consumers order by `walletVersion`. Cost if wrong: a second publisher can still send a wallet's
  events out of order, as before (section 14).
- **P-07 The lock path makes fewer round trips** (this commit). One query finds the transaction by key, and
  falls back to the external id; the key wins when they name different rows, which a test pins. The two
  balance events of a transaction are inserted in one statement. The outcome of a reference is one query. That
  query has an `OR` of two arms, each of which matches a partial unique index on the reference. A single `kind
IN (...)` over all four kinds was tried first and rejected: `EXPLAIN (ANALYZE, BUFFERS)` on 20,000 rows showed
  a sequential scan at 3.9 ms, against 0.09 ms for the arms. The idle service time of the lock path fell by about
  a quarter. Cost if wrong: an `OR` that the planner stops using would scan again, so the plan is worth
  rechecking after any index change.
- **P-08 Phase metrics are summaries, with no identifier in any label** (`ceb60c7`). Each summary carries the
  count, the sum and the maximum. The instrumentation added no measurable CPU at 100 req/s: the four runs of the
  baseline and of the instrumented build sit within the spread of the runs. A static test reads the source and
  fails on an identifier label. Cost: no percentile per process; the load test measures percentiles.
- **P-09 Zod is not adopted.** The validators are about 400 lines across the modules, and most of that is field
  checks that produce the stable codes the provider relies on (`IDEMPOTENCY_KEY_REQUIRED`, `INVALID_MONEY`,
  `INVALID_REQUEST`). A schema library would add a dependency, and it would still need the domain check of
  `Money`, which must stay in the domain (section 6.1). After the shared parser of P-03 the duplication between
  HTTP and the queue is one function. Zod would remove little, so the change is not made. Cost if wrong: a few
  more lines to read.
- **P-10 Authentication stays one lookup per request, and its result is not cached.** On an idle system the
  lookup takes 0.8 ms (mean, 3000 calls). The 7 ms seen under load is contention for the two saturated CPUs. A
  cache would keep a revoked key valid for as long as it lived. Cost: one database round trip per request.
- **P-11 The 4-CPU load figure is measured with the generator on the same CPUs.** Before this review's
  changes, the 4-CPU run failed the generator-lag constraint at 50 req/s, because the stack had every CPU and the
  generator shared them. After the batching and the lock-path changes, the same run passed every step up to 400
  req/s, with the lag inside its limit. The figure is therefore reported, with that caveat: it is a lower bound for
  the stack alone, and the ceiling above 400 was not searched. The 1- and 2-CPU figures leave CPUs to the generator.

## Q. The protected mode

- **Q-01 An optional Nginx edge limits each client address, and it is the only public entry in protected mode.**
  The default mode is unchanged. The protected mode is an override file, so `docker compose up` still runs
  without it. The limit is keyed on the TCP peer. The edge never reads a forwarding header for a quota, and it
  sets the forwarding headers itself. Writes and reads have separate quotas, with explicit bursts and a connection
  limit. A refusal is 429, as JSON, with `Retry-After`. Health checks are not limited. Evidence: the eleven tests of
  `test/edge`, and two mutations that each made one test fail (a key on `X-Forwarded-For` failed the spoofing test,
  and a shared key failed the isolation test). The cost is one hop: about 0.1 ms at the median and 0.3 ms at p95,
  measured once in each configuration (`docs/edge/results`). Cost if wrong: a deployment behind a load balancer
  must add that balancer's address with `set_real_ip_from`, or every client shares the balancer's quota.
- **Q-02 The protected mode is not a security boundary, and it says so.** A per-address limit does not stop a
  distributed attack. Keys still travel in plain HTTP, so TLS belongs in front of the edge. The architecture
  document, section 15, states both, and the README repeats them.
- **Q-03 The image for the sandbox is built from a scratch context.** The repository's Dockerfile needs the
  package registry through the sandbox's TLS proxy, which the build container does not trust. The verification used
  an image built from the same sources, with the sandbox CA added, outside the repository (as
  `ARCHITECTURE.md` section 14 already records). The repository's Dockerfile is unchanged. An evaluator outside the
  sandbox builds it with `docker compose up --build`.
