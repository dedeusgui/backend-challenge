# Decisions

Every technical decision of this project, with the reason, the trade-off, the evidence and the
status. Decisions with their own record are in [`docs/adr`](docs/adr). The rules of the business
are in [`ARCHITECTURE.md`](ARCHITECTURE.md) section 13.

Status values:

- **Accepted**: decided, implemented, and tested.
- **Open**: implemented, but the owner of the specification must confirm it. Each open item is
  listed again in [`docs/INVARIANT_REVIEW.md`](docs/INVARIANT_REVIEW.md), section 2.
- **Superseded**: replaced by a later decision, which is named.

## B. Money

| ID   | Decision                                                                                                                 | Why                                                                    | Trade-off                                        | Evidence                                       | Status   |
| ---- | ------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------- | ------------------------------------------------ | ---------------------------------------------- | -------- |
| B-01 | Money is a decimal string with two places, in `NUMERIC(20,2)`, and at most 18 integer digits. It is never a JS `number`. | Floating point loses cents. | B-02 | `decimal.js` with precision 40 for the arithmetic, so that sums of two-place values never round.                         | A precision of 20 lost a centavo at 999,999,999,999,999,999.99 + 0.02. | Slower than integers. | B-03 | An amount is positive for every kind except LOSS, which may be zero. | B-04 | Amounts are sent as `{ "amount": "25.00", "currency": "BRL" }`.                                                          | The amount and its currency always travel together.                    | The payload is larger than a bare number.        | `src/shared/http/**`, `test/e2e/*.test.ts`     | Accepted |

## C. Domain rules

| ID   | Decision                                                                                                                                            | Why                                                                | Trade-off                                                          | Evidence                                                   | Status   |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------ | ---------------------------------------------------------- | -------- |
| C-01 | `Wallet` validates before it mutates. Its balance never goes negative, and `version` starts at 1 and changes only with a balance change.            | The aggregate is the one place where balance rules live.           | Every change builds a new state.                                   | `src/modules/wallet/domain/wallet.ts`, wallet unit tests   | Accepted |
| C-02 | Ledger entries are immutable. Triggers refuse update, delete and truncate. Each entry checks `balanceBefore ± amount = balanceAfter`.               | The ledger is the audit trail.                                     | A mistake cannot be fixed in place. It is reversed by a new entry. | triggers in migration 1; schema tests                      | Accepted |
| C-03 | The rules of each kind are one table, `KIND_RULES`: balance effect, ledger direction, reference rules, and whether a provider may submit the kind.  | A reviewer can read every kind in one place.                       | The table must be kept in step with the schema CHECKs.             | `src/modules/wagering/domain/wager-transaction-kind.ts`    | Accepted |
| C-04 | A transaction moves through explicit states (`PENDING`, `PENDING_REFERENCE`, `PROCESSED`, `REJECTED`, `FAILED`). A terminal state never reopens.    | The state machine is checked in code and in the database.          | More code than a status string.                                    | `wager-transaction.ts`, `wager_status_shape`               | Accepted |
| C-05 | OPENING is written only by the system, under the provider `system`, and a provider may never submit it.                                             | The opening credit is not a provider's operation.                  | None.                                                              | `open-wallet.use-case.ts`, unit test "OPENING is internal" | Accepted |
| C-06 | A business rejection is a persisted row with a stable `failureCode`, and an HTTP 422. A rejected row changes no balance and writes no ledger entry. | The outcome is auditable and the provider knows whether to resend. | A rejected request still writes a row.                             | `transaction-settlement.ts`, "rejected no effect" tests    | Accepted |
| C-07 | A reversal that would overdraw is `REVERSAL_WOULD_OVERDRAW`, distinct from `INSUFFICIENT_BALANCE`.                                                  | The two situations need different operational responses.           | Two codes for one arithmetic check.                                | `transaction-settlement.ts`, wagering tests                | Accepted |
| C-08 | Failure codes are stable and machine-readable. Renaming one is a breaking change.                                                                   | The provider branches on them.                                     | Codes cannot be renamed casually.                                  | `src/modules/wagering/domain/failure-code.ts`              | Accepted |
| C-09 | A replay returns the original result, with the balance observed at that time (`resulting_balance`). A replay is not counted as a transaction.       | The same request always gets the same answer.                      | The balance in a replay may be older than the current balance.     | `process-wager-transaction.use-case.ts`, replay tests      | Accepted |

## D. Reference rules (business interpretations, IDs R-01 to R-13)

The specification leaves these open. Each is in `ARCHITECTURE.md` section 13, and each was
reviewed in `docs/INVARIANT_REVIEW.md`.

| ID   | Decision                                                                                                                                              | Why                                                                                                                           | Trade-off                                                                               | Evidence                                                                                | Status   |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- | -------- |
| R-01 | A WIN and a LOSS **must name** the BET they settle. The spec says a WIN "pode referenciar" its BET.                                                   | Without the link, a result cannot be checked against a REFUND or a second result. A BET could pay twice.                      | It narrows the spec. A WIN without a BET is now refused.                                | `KIND_RULES`, `wager_reference_shape`, "a WIN or LOSS without the reference" tests      | Open     |
| R-02 | A BET has **at most one** PROCESSED result, a WIN or a LOSS. A second result is `REFERENCE_ALREADY_SETTLED`.                                          | Two WINs on one BET credited twice. Found by review, and fixed.                                                               | None for the owner, once R-01 holds.                                                    | `wager_one_processed_result_per_reference`, settlement, "a BET pays once" test          | Accepted |
| R-03 | A REFUND applies **only** to a BET with no result. After a WIN or a LOSS it is `REFERENCE_ALREADY_SETTLED`.                                           | The owner's decision.                                                                                                         | A provider sends a ROLLBACK of the WIN instead.                                         | `mustBeUnsettled`, "a REFUND is refused once the BET has a WIN" test                    | Accepted |
| R-04 | A ROLLBACK applies in **every state** of the transaction it reverses: a BET with or without a result, a WIN, or a REFUND.                             | The owner's decision. A ROLLBACK is the general reversal.                                                                     | After a WIN, rolling back the BET returns the stake and keeps the WIN credit. See R-05. | `mustBeUnsettled: false`, "a ROLLBACK applies after the BET has a WIN" test             | Accepted |
| R-05 | The economic effect of R-04 is that a round is cancelled only when the WIN is rolled back too.                                                        | Consequence of R-04, which the owner has to accept.                                                                           | A provider that rolls back only the BET leaves the winnings in the wallet.              | "a ROLLBACK applies after the BET has a WIN" test (it pins the behaviour)               | Open     |
| R-06 | A referenced transaction is reversed **at most once**, whatever the kind of reversal.                                                                 | Spec rule 4 says "pelo mesmo tipo de operação". Read literally it allows REFUND then ROLLBACK, which credits the stake twice. | The stricter rule refuses a case the spec may allow.                                    | `wager_one_processed_reversal_per_reference`, "competing reversals" tests               | Open     |
| R-07 | A reversal's amount equals its reference's amount. A WIN's amount is not bound to its BET.                                                            | Reversals restore exactly what was taken. A WIN settles an independent amount.                                                | A partial reversal is out of scope.                                                     | `amountMustMatch`, "reversal must match" test                                           | Accepted |
| R-08 | A reversal or a result on a BET that was already reversed is `REFERENCE_ALREADY_REVERSED`.                                                            | Nothing after a reversal may move the balance again.                                                                          | None.                                                                                   | settlement, "a WIN cannot settle a BET that was already refunded"                       | Accepted |
| R-09 | A reference must belong to the same provider, wallet and round. The database checks the three. The domain checks the player and the currency.         | Round, wallet and provider are composite keys. A rejected row keeps its player and currency (see C-06).                       | The player and currency are not a database constraint.                                  | composite foreign keys in migrations 1 and 5; `sharesContextWith`                       | Accepted |
| R-10 | A transaction whose reference is missing is held as `PENDING_REFERENCE`, and announced by an event.                                                   | Out-of-order delivery is normal (spec section 3).                                                                             | A held transaction has no result until its reference arrives or the limit is reached.   | `pending-reference.test.ts`, `WagerTransactionPendingReference` event                   | Accepted |
| R-11 | A held transaction is retried with backoff: 1 s, doubling, capped at 5 min, for at most 6 attempts. Then it is `REJECTED` with `REFERENCE_NOT_FOUND`. | Bounded work, and a clear end for a reference that never arrives. See ADR 0005.                                               | A reference that arrives after the 6th attempt is refused.                              | `reference-retry-policy.ts`, its cap test (mutation checked)                            | Accepted |
| R-12 | Each unit of work has one settlement function, `TransactionSettlement.settle`, called by HTTP, by the queue and by the reference worker.              | One financial decision in one place. The rules cannot drift between paths.                                                    | Every caller must hold the wallet lock first.                                           | `transaction-settlement.ts`                                                             | Accepted |
| R-13 | The idempotency key is per provider. The same external id under another key replays if the payload matches, and conflicts if it does not.             | A provider's key space is its own.                                                                                            | None.                                                                                   | `wager_external_identity_key`, `wager_idempotency_key`, "same key, other payload" tests | Accepted |

## E. Concurrency and locking

| ID   | Decision                                                                                                                                                         | Why                                                                                              | Trade-off                                                                                 | Evidence                                                               | Status   |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- | -------- |
| E-01 | The unit of concurrency is the `walletId`. Operations on different wallets never wait for each other.                                                            | The challenge's section 8.                                                                       | A hot wallet serialises its operations.                                                   | `hot-wallet.test.ts`, `distinct wallets` tests                         | Accepted |
| E-02 | Every financial path takes a **pessimistic row lock** on the wallet (`FOR UPDATE`) before it checks the idempotency key or changes anything. See ADR 0001.       | A lock is simpler to reason about than retries, and the lock is the first thing every path does. | Requests on the same wallet queue behind each other.                                      | `findForUpdate`; the lock mutant (M1) is caught by the zero-retry test | Accepted |
| E-03 | The version guard in `save` stays as a second line of defence, with at most 3 attempts on `ConcurrencyConflictError`. Exhaustion is `503` with `retry-after: 1`. | A lock bug must not become a lost update.                                                        | Retries add latency when they happen. With the lock, they never happen (measured).        | `MAX_CONCURRENCY_ATTEMPTS`, `save`, the zero-retry assertion           | Accepted |
| E-04 | Reconciliation takes a **shared** lock (`FOR SHARE`) on the wallet, so a debit waits while it reads the balance and the ledger.                                  | Without it a debit between the two reads is reported as a divergence that does not exist.        | A debit of that wallet waits for one reconciliation.                                      | `findForShare`, `reconciliation-consistency.test.ts`, commit `4d6dc01` | Accepted |
| E-05 | Read paths take no lock. Only reconciliation takes a shared lock.                                                                                                | Reads must never queue behind a financial write.                                                 | A read may see a state that is one commit old.                                            | `WalletQueries`, `WagerQueries`                                        | Accepted |
| E-06 | The outbox claim uses `FOR UPDATE SKIP LOCKED`.                                                                                                                  | Two publishers should not wait for each other.                                                   | Removing it changes nothing a test can see (mutant M3). The lease predicate keeps safety. | `mikro-orm-outbox.store.ts`; M3 recorded in `TEST_STRATEGY.md`         | Accepted |
| E-07 | Lock waits are **not measured**. `concurrency_conflicts_total` counts lost races only.                                                                           | Measuring the wait needs instrumentation that was not added.                                     | A slow lock is invisible in the metrics.                                                  | `process-wager-transaction.use-case.ts`                                | Open     |

## G. Messaging and the transactional outbox

| ID   | Decision                                                                                                                                               | Why                                                                             | Trade-off                                                                              | Evidence                                                            | Status   |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------- | -------- |
| G-01 | An outbox row is written in the same transaction as the financial change. No event is published before its commit. See ADR 0004.                       | A crash cannot publish an effect that did not happen.                           | The publisher is a second process, and it lags.                                        | `outbox_messages` in the transaction; `INV-05`                      | Accepted |
| G-02 | Publishing is at-least-once. Each event has a stable id, and that id is the SQS deduplication id.                                                      | Retries are safe if consumers can tell a repeat.                                | Within SQS's five-minute window a repeat is dropped by the broker.                     | `SqsEventTransport`, `outbox-publisher.test.ts`                     | Accepted |
| G-03 | The publisher claims rows with a lease token (30 s by default), and it marks a row only while it still holds the token.                                | Two publishers never send the same event at the same time.                      | A crashed publisher delays its events by the lease.                                    | `claimDue`, `complete`; mutants M4 caught by the two-publisher test | Accepted |
| G-04 | The outbox publishes in batches of 20, with a 500 ms idle delay. A failed send is retried with backoff from 1 s, doubling, capped at 60 s.             | Simple and bounded.                                                             | Under load the publisher lags: see G-05.                                               | `outbox-message.ts`, `OUTBOX_*` settings                            | Accepted |
| G-05 | The publisher sends one event at a time. Under the load test its average lag was several seconds. Parallel or batched sends were not built.            | Simplicity first. The lag was measured, and it is recorded.                     | **A known bottleneck.** See `docs/LOAD_TEST_RESULTS.md`.                               | `docs/LOAD_TEST_RESULTS.md`, `ARCHITECTURE.md` section 14           | Open     |
| G-06 | The command consumer acknowledges a message only after its transaction commits. The inbox row is written in the same transaction.                      | A crash before the ACK redelivers, and the inbox turns the repeat into a no-op. | A message can be processed twice in the broker, and once in the database.              | `wager-command-consumer.ts`, the crash-after-commit tests           | Accepted |
| G-07 | A permanent failure goes to the dead-letter queue. A transient failure goes back to the queue with visibility backoff: 2 s, doubling, capped at 300 s. | A bad message must not block the group. A transient one must be retried.        | None.                                                                                  | `failure-classification.ts`, `retryDelaySeconds`                    | Accepted |
| G-08 | The broker redrive moves a message to the dead-letter queue after **10** deliveries. It was 5.                                                         | Ten outlasts a short outage. Five could dead-letter a valid command during one. | A poisoned message takes longer to leave the queue.                                    | `docker/localstack/init-sqs.sh`, `broker-redrive.test.ts`           | Accepted |
| G-09 | The consumer long-polls for 1 s, takes batches of 10, and has a 30 s visibility timeout by default.                                                    | A short poll misses messages that exist.                                        | A message in flight for 30 s blocks its group for that long.                           | `wager-command-consumer.ts`, `CONSUMER_VISIBILITY_SECONDS`          | Accepted |
| G-10 | The events queue is FIFO, grouped by the aggregate id (the wallet). The body is the event envelope.                                                    | Events for one wallet keep their order.                                         | Events of different wallets can overtake each other.                                   | `SqsEventTransport`, ARCHITECTURE section 8                         | Accepted |
| G-11 | Every event has an envelope: `eventId`, `eventType`, `aggregateId`, `correlationId`, `causationId` when known, `occurredAt`, `version`, and `data`.    | A consumer can version and trace an event.                                      | The envelope is larger than the data.                                                  | `src/shared/domain/integration-event.ts`                            | Accepted |
| G-12 | The queue is a trusted internal channel. Its business fields are validated by the domain. It has no authentication of its own.                         | The challenge's section 2.                                                      | Anyone who can write to the queue can submit an operation. In AWS, IAM is the control. | `ADR 0007`, ARCHITECTURE section 12                                 | Accepted |

## H. Workers and processes

| ID   | Decision                                                                                                                                                 | Why                                                 | Trade-off                                                                        | Evidence                                                                    | Status   |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- | -------------------------------------------------------------------------------- | --------------------------------------------------------------------------- | -------- |
| H-01 | One worker process runs three loops: consume, publish and resolve references. Each pass is guarded, so a failure is logged and does not stop the worker. | A transient outage must not end the process.        | During a long outage each loop logs once a second.                               | `src/worker/run-worker.ts`, `run-worker.test.ts`                            | Accepted |
| H-02 | A failed pass waits a fixed 1 s, with no exponential backoff, before it runs again.                                                                      | Simple, and enough for a dependency that restarts.  | Hides a long outage behind a steady stream of log lines.                         | `DEFAULT_ERROR_DELAY_MS`                                                    | Open     |
| H-03 | `SIGTERM` and `SIGINT` set a flag. Each loop finishes the pass in progress and then exits with code 0. Compose gives 30 s to stop.                       | A batch in progress is acknowledged, not abandoned. | A pass that takes longer than 30 s is killed by Docker.                          | `worker.ts`, `distributed-contention`, `process-crash-and-shutdown.test.ts` | Accepted |
| H-04 | `api` and `worker` restart after a crash (`restart: unless-stopped`). `migrate` never restarts, because it runs once.                                    | A crashed process must not stay down.               | Configuration only. No test runs a restart.                                      | `docker-compose.yml`, `docker compose config`                               | Accepted |
| H-05 | Migrations run in a one-shot `migrate` service. `api` and `worker` start only after it succeeds.                                                         | The schema is ready before any process needs it.    | A failed migration stops the stack, which is the intent.                         | `docker-compose.yml`                                                        | Accepted |
| H-06 | Every migration is reversible, and the schema suite rolls back to zero and re-applies.                                                                   | A bad migration can be undone in development.       | A rollback that would lose data needs a data plan. None is needed in this build. | `test/integration/schema/migrations.test.ts`                                | Accepted |
| H-07 | Processes share nothing in memory. Each has its own pool, clients and metrics.                                                                           | The distributed proof needs independent processes.  | Metrics are per process.                                                         | `ProcessCluster`, `three-processes.test.ts`                                 | Accepted |

## I. HTTP contract

## K. Observability

| ID   | Decision                                                                                                        | Why                                                                               | Trade-off                                                                    | Evidence                                                 | Status   |
| ---- | --------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- | -------------------------------------------------------- | -------- |
| K-01 | Logs are one JSON object per line, with only declared fields. The type has no field for an amount or a payload. | A payload cannot leak into a log by accident.                                     | A new field needs a change to the type.                                      | `structured-log.ts`, "cannot carry a money field"        | Accepted |
| K-02 | An error is logged with its class and its code, never its message, because a message can carry a payload.       | The message of a driver error can echo a row.                                     | The message is not available to an operator.                                 | `describeError`, its unit test, the integration log test | Accepted |
| K-03 | Metrics are in-memory counters and summaries per process, on `GET /metrics`. There is no Prometheus endpoint.   | The challenge does not ask for a dashboard. The format is readable as JSON.       | No aggregation across processes, and no dashboard. See the reference review. | `metrics.ts`, `metrics-http.test.ts`                     | Accepted |
| K-04 | Summaries hold a count, a sum and a maximum. They do not hold percentiles.                                      | A percentile needs a histogram. The load test measures percentiles on the client. | No server-side p95.                                                          | `metrics.ts`, `docs/LOAD_TEST_RESULTS.md`                | Accepted |

## L. Testing

| ID   | Decision                                                                                                                                                                        | Why                                                                                          | Trade-off                                                                 | Evidence                                                                   | Status   |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- | -------------------------------------------------------------------------- | -------- |
| L-01 | Unit tests use real domain objects. Integration, e2e and concurrency tests never replace PostgreSQL or SQS with a mock.                                                         | The challenge forbids tests that replace the database and the queue.                         | Unit tests need no infrastructure, but they prove less about persistence. | `TEST_STRATEGY.md`                                                         | Accepted |
| L-02 | Each database suite has its own database, and its teardown checks `balance == ledger`. Each SQS suite has its own queues.                                                       | Suites run in any order, and a violated invariant fails the suite that caused it.            | The checks add time to teardown.                                          | `test-database.ts`, `sqs-test-queues.ts`                                   | Accepted |
| L-03 | Process-level tests use `Bun.spawn`. Test-only entrypoints in `test/support` stop a process at a chosen point. The seams `faults` and `decorateUnitOfWork` exist only for them. | The crash must be a real exit of a real process, not an exception.                           | Production code carries two optional test seams.                          | `crashing-worker.ts`, `crashing-before-commit-worker.ts`, `slow-worker.ts` | Accepted |
| L-04 | Mutation testing is manual, and each mutant is recorded with its result, including the one that survived.                                                                       | No mutation tool is in the stack, and a recorded survivor is more useful than a silent pass. | It does not run in CI.                                                    | `TEST_STRATEGY.md`, "Mutation evidence"                                    | Accepted |
| L-05 | A load test is an optional differential. It writes a report, and it is outside `check:all`.                                                                                     | It is slow, and its numbers depend on the machine.                                           | Not run on every change.                                                  | `test/load/load-test.ts`, `docs/LOAD_TEST_RESULTS.md`                      | Accepted |
| L-06 | A suite never waits with a sleep to synchronise. It polls the database or the readiness endpoint with a bound. ## Decisions that are not decisions

These are facts of the environment, and the project depends on them without choosing them:

- The sandbox has no published CI run. The workflow was validated for syntax and not executed on GitHub.
- The LocalStack behaviour is LocalStack's, and an AWS deployment was not made.
