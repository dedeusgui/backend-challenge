## Methodology

- 4000 operations, 64 concurrent lanes, 50 wallets opened with 1000.00 BRL.
- Each lane sends one request at a time, and the lanes round-robin over the 3 API processes.
- 10% of the operations contend for one hot wallet. 5% re-send an earlier request with its original key.
- Every operation is a BET of 5.00 BRL. A business rejection (422, insufficient balance) is an expected answer, not an error.
- Latency is measured by the client, from sending to reading the body. The server summaries have only count, sum and max, so the percentiles below are client-side.
- After the run, the outbox is drained, and the invariant `wallet.balance == ledger sum` is checked for every wallet.
